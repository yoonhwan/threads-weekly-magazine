에이전트가 틀린 기억을 막는 세 시점: 세션 사이, 답변 직전, 저장 직전

Anthropic의 dreaming은 세션 사이에 메모를 원본 기록과 대조해 고친다. NVIDIA Auto Ontology는 에이전트가 만든 SQL을 인증된 업무 정의로 검증한다. AutoRAG Agent는 판단 전용 모델 Jev로 저장 직전에 근거를 거른다. 셋 다 '에이전트가 자신 있게 틀리는 문제'를 서로 다른 시점에서 막는다.

Anthropic은 11월 6일 엔지니어링 블로그에 '에이전트 기억의 구성 요소'를 올렸다. 핵심은 dreaming이다. 일하는 중에는 메모를 가볍게 남기고, 세션 사이에 Claude가 원본 기록을 다시 읽어 틀린 메모를 고치고 위키로 묶는다. 모델 가중치는 바뀌지 않는다. 블로그의 수치는 전부 Anthropic 자체 평가다. 파일 약 35만 개(약 4.2억 토큰)로 위키를 만들고 dreaming을 2세션에서 128세션으로 늘리자, 질문 25개의 채점 기준 충족률이 위키만으로 13%에서 48%가 됐다. 검색을 더하면 54%에서 61%이고 검색만 쓰면 53%였다. 같은 글이 한계도 적는다. 한 단일 문서 과제에서는 위키의 이득이 뚜렷하지 않았고, 다른 과제에서는 위키가 원본 파일보다 1.77배 커졌다(AI 뉴스 데일리 요약). 기능 자체는 새 소식이 아니다. 토큰포스트에 따르면 dreaming 제품 발표는 5월 19일이었고 지금도 접근을 신청한 사람만 쓰는 연구 프리뷰이며, Harvey 테스트의 '작업 완료율 약 6배'는 비교 조건이 공개되지 않았다. HN(148포인트, 댓글 73개)의 반응은 갈렸다. 한쪽은 '메모를 .md 파일에 써서 다시 넣는 일을 dreaming이라 부르는 건 마케팅'이라 했고, 다른 쪽은 '모든 하네스에서 자동 메모를 꺼 뒀고 만들어진 메모의 95%는 지운다'고 했다. NVIDIA Auto Ontology는 같은 문제를 다른 시점에서 푼다. 메타데이터로 업무 용어, 지표, 관계를 미리 정리하고, 에이전트가 만든 SQL을 인증된 정의와 데이터 계보에 대조해 출처와 함께 돌려준다. AI타임스에 따르면 NVIDIA는 '온톨로지 생성 시간 90% 단축'을 내세웠지만 답변 정확도 수치는 내놓지 않았고, 자동 생성한 정의는 담당자의 검토와 승인이 필요하다. HN(290포인트, 댓글 139개)에서는 'NVIDIA API 키가 꼭 필요하냐'는 질문이 나왔고, GeekNews 댓글에는 키는 NVIDIA 호스팅을 쓸 때만 필요하다는 답이 달렸다. 조회 시점 GitHub 스타는 9,776개다. AutoRAG Agent의 Jev는 저장 직전을 지킨다. Threads 글과 README에 따르면 답변을 뒷받침한다고 Jev가 판단한 인용 근거만 memory.json에 저장하고, 그 기억은 이후 검색에서 참고용으로만 쓴다. 이 글은 개인 프로젝트의 사용법 소개이고 레포는 스타 5,402개(기존 Python AutoRAG 포함), Apache-2.0이다.

'AI 슬롭을 줄이려면 에이전트에게 좋은 레퍼런스 5곳을 줘라'는 글의 댓글에서는, MCP로 실시간 조회하면 화면마다 결과가 달라지니 한 번 확정해 파일로 고정하라는 제안이 나왔다. Meta의 Astryx는 그 고정 쪽에 가까운 구조를 제품으로 내놓았다.

Threads의 '디자인 슬롭 방지' 글은 에이전트에게 레퍼런스 5곳(jiro.build, Design Spells, Refero Styles, Supahero, Mobbin)을 주라는 내용이다. 알맹이는 댓글에 있었다. 한 댓글은 MCP로 실시간 조회하면 실행마다 다른 조각이 나와 화면 간 일관성이 깨진다며, 레퍼런스 세트를 한 번 확정하고 토큰, 간격, 상태를 파일로 기록해 에이전트가 다시 읽게 하라고 했다. MCP는 고르는 도구이고 빌드 기준은 파일이라는 구분이다. 다른 댓글은 이 사이트들도 서로를 참조해 만든 것이라 결국 슬롭이 더 늘 뿐이라고 반박했다. Meta의 Astryx는 이 논쟁과 맞닿은 제품이다. 아래는 우리의 해석인데, '고정' 쪽에 가까운 구조다. swizzle로 컴포넌트 전체 소스를 프로젝트로 꺼내 직접 소유하고, 테마는 CSS 변수 덮어쓰기 묶음이며, API와 문서와 CLI를 사람과 AI 어시스턴트가 같은 레퍼런스로 쓰도록 함께 설계했다. 공식 블로그는 접근성을 갖춘 컴포넌트 150개 이상, 내부 8년, 앱 13,000개 이상을 내세운다. InfoQ는 CLI와 MCP 도구가 함께 제공된다고 전한다. 그런데 이 소식은 새롭지 않다. HN에는 6월 24일에 올라왔고 반응은 12포인트, 댓글 2개였다('matcha 테마가 마음에 든다', 'Meta를 믿기는 어렵다'). 공개일은 출처마다 다르다. GCN은 6월 28일, Life at Meta 게시물은 7월 2일이다. 테마 수도 MarkTechPost는 7종, GCN은 10종(gothic, y2k, brutalist 포함)이라고 쓴다. 컴포넌트 수는 MarkTechPost가 문서 사이트 기준 160개 이상이라고 덧붙인다. 레포 주소는 HN 글이 facebook/astryx, 지금은 meta/astryx다. 조회 시점 GitHub 스타 14,488개, MIT, 베타, React 19 이상이다. KittenTTS 2는 1.7B 파라미터를 1비트로 줄인 음성 언어 모델이다. 양자화 가중치는 506MiB이고 기본 음성 47개, 5~30초 샘플 음성 복제를 지원하며 CPU에서 실시간으로 돈다고 README는 적는다. 그런데 같은 README의 사전 요건은 'CUDA GPU 약 8GB 여유, 또는 RAM 약 6GB의 CPU'다. 파일은 506MiB여도 메모리는 그 열 배 이상 잡는 셈이다. 한국어는 Threads 글이 20개 언어에 포함된다고 썼고, 우리가 확인한 README 발췌에서는 언어 목록까지 확인하지 못했다. 글쓴이도 한국어 발음 품질은 직접 테스트하라고 단서를 달았다. 허깅페이스 기준 모델은 9월 30일에 만들어졌고 다운로드 75,745회, 좋아요 213개이며, GitHub 스타는 Threads 글 시점 16,412개에서 조회 시점 16,810개가 됐다. 이전 세대(0.8, 15M~80M 파라미터, 25MB부터)는 HN에서 3월 Show HN이 561포인트·댓글 181개, 2025년 8월 첫 Show HN이 1,003포인트·댓글 361개를 받았다. KittenTTS 2 자체를 다룬 HN과 GeekNews 글은 찾지 못했다. NVIDIA RE-USE는 960만 파라미터, FP32 기준 38.4MB, 30층 양방향 Mamba 모델이다. 허깅페이스 릴리스는 10월 22일이고 NVIDIA의 X 소개가 10월 30일, AI타임스 보도가 11월 2일이라 '이번 주 공개'로 읽히기 쉽다. URGENT 2025 전체 세트에서 PESQ 2.57(UniPASE 2.17), STOI 0.78(0.76), 화자 유사도 0.86(0.81), 문자 정확도 89.17(87.28)로 더 큰 모델보다 앞서지만, DNSMOS(3.29 대 Sidon 3.34)와 UTMOS(2.94 대 Sidon 3.21, UniPASE 2.96)는 뒤진다. 이 수치는 NVIDIA 자체 발표다. 학습 언어는 영어, 독일어, 스페인어, 프랑스어, 중국어이고 한국어는 없다(모델 카드는 언어에 종속되지 않는다고 설명). 공식 추론 환경은 Linux와 Ampere GPU이고 mamba-ssm이 필요해서, Oossa는 작은 크기만으로 개인용 기기에서 바로 실행된다고 보기는 어렵다고 지적했다. 파일 크기, 파라미터 수, 필요한 하드웨어는 서로 다른 숫자다.
